# Git 方案下的下发者旅程

> 系列文档之二，总览见 [`GIT_UX_JOURNEYS_OVERVIEW.md`](./GIT_UX_JOURNEYS_OVERVIEW.md)。
> 角色：部门主管 / 平台管理员（下发的发起方与治理方）。
> 基调：正向走查——先写 Git 方案如何把体验做对，再列补足项。
> 判定图例：✅ 天然满足 · 🔧 补足后满足 · 📌 需决策

## 来源标注约定（重要）

本篇每个功能点标注来源，避免把「作者认为该有的」误读成「V4 承诺的」：

| 标注 | 含义 |
|---|---|
| `[现状]` | 代码里已实现，Git 方案下需保住 |
| `[V4 §x]` | V4 提案明确写了 |
| `[推导]` | V4 未写，但属该架构的必然要求（如废弃 Content 字段 ⇒ 必须定义详情接口替代方案） |
| **`[新增建议]`** | ⚠️ **非现状、非 V4，是本文提出的产品增强**。与 Git 迁移无依赖关系，可独立取舍——评审时可直接跳过 |

`[新增建议]` 类条目统一汇总在文末「可选增强」一节，不进主线补足清单。

### D1 我把审核过的技能下发给团队

> 作为部门主管，我希望把一个我确认过内容的技能推给团队，以便统一团队的工作方式。

**Git 方案下的流程**：

1. （主管）在 marketplace 找到技能，进入下发面板 —— 列表来自 DB 索引，体验不变（server）
2. 面板显示该技能的**当前版本 = commit sha + 提交时间 + 作者**，主管确认"我下发的就是这一版"（server 读 `capability_items.git_sha`）
3. 选目标（人 / 部门）、权限模式、附言，提交（server：建 `ItemDistribution` + receipt，状态机原样保留）
4. 下发记录**自动锚定当时的 sha**（db：`pinned_sha`）
5. 接收方收到通知，下一轮 sync 拿到 **pinned_sha 对应的内容**（server 按 sha 从 Gitea raw 取）

**V4 已支持**：下发状态机与 target 不变（附录 C.2.1，target 引用不可变 user_id）；按 sha 取文件是 Gitea raw API 原生能力（§10.2 `GET .../raw/{filepath}?ref={sha}`）。

**需补足**：

| 补足项 | 组件 |
|---|---|
| `ItemDistribution` 增加 `pinned_sha` / `pinned_ref` 字段（可空 = 跟随最新） | db |
| 下发面板展示当前 sha 并默认锚定 | web |
| 内容读取按 receipt 的 pin 取（列表/详情/download 一致） | web |
| 私有技能的内容授权传递：下发时授 collaborator，或内容层加 receipt 旁路（见 D9） | web / gitea |

**判定**：🔧 —— 补足后**优于现状**：现状下发没有版本概念，"我下发的是什么"说不清；Git 方案里每一次下发天然可锚定到一个 commit。

### D2 我要控制团队拿到的版本：锁定或跟随

> 作为下发者，我希望在"锁定当前版本"和"自动跟随最新"之间选择，以便对推给团队的内容负责。

**Git 方案下的流程**：

1. 下发面板提供版本策略：**锁定**（默认，`pinned_sha=abc123`）/ **跟随**（`pinned_ref=main`）
2. 锁定模式：作者继续迭代不影响团队，团队环境稳定
3. 跟随模式：作者 push 后 webhook 感知（§10.3），接收方下轮 sync 自动更新
4. 任何时刻主管可在管理面板把 pin 推到新 commit（"升级下发"）

**V4 已支持**：版本即 commit，无需另造版本表；ref 语义 §14.1 已引入（`source_repo_ref`）。

**需补足**：

| 补足项 | 组件 |
|---|---|
| 版本策略字段与切换操作 | db / web |
| 跟随模式加护栏：仅允许跟随受保护分支（§13.4 branch-protection 已有设计，接过来即可） | web / gitea |

**判定**：🔧 —— 这是 Git 方案的**代表性增益**：现状完全做不到，补一个字段 + 一个面板即可获得。

### D3 作者发新版本后，我决定何时升级团队

> 作为下发者，当作者发布新版本，我希望先看到变化、再决定是否推给团队，以便避免"作者一改、全员被动变更"。

**Git 方案下的流程**：

1. `[V4 §10.3]` 作者 push → webhook 更新 `git_sha`（server）
2. `[推导]` 下发记录锚定的 sha 与 repo 当前 HEAD 出现差异，即"该下发落后了"——这个判定在 Git 方案下**天然可计算**（现状因为没有版本锚定，连"落后"这个概念都无法表达）
3. `[推导]` 主管决定是否把 pin 推到新 sha；不动则团队环境保持稳定

**V4 已支持**：webhook 同步与 `git_sha`（§10.3、§14.1）让"两个版本之间差了什么"变得可查——Gitea compare API 存在于 §10.2 的调用清单中（V4 中该 API 服务于 sync worker 拉取变更文件清单，未定义面向下发者的用途，但能力是现成的）。

**需补足**：

| 补足项 | 来源 | 组件 |
|---|---|---|
| 下发面板展示"当前锚定版本 vs 最新版本"的差异状态（静态展示，无需 JOB） | `[推导]` | web / portal |
| 手动"更新到最新版本"操作（把单条下发的 pin 推到新 sha） | `[推导]` | web |

**判定**：🔧 —— 相比现状「作者改了没人知道」（更新信号靠作者手写版本号），Git 方案让下发者第一次能看见"我的下发落后了"。

> 主动式的落后检测 JOB、diff 预览面板、批量升级操作属产品增强，见「可选增强」E-3。

### D4 升级前，内容先过安全扫描

> 作为下发者，我希望推给团队的每个版本都过了扫描，以便不把风险批量放大。

**Git 方案下的流程**：

1. 作者 push → webhook → 触发扫描，短路键用 `git_sha`（server，§12 已设计，含双写兼容期）
2. 落后提醒里带扫描结论：「新版本 abc123 · 扫描通过 ✓」
3. 未扫描或未通过的 commit，升级按钮置灰（策略可配）

**V4 已支持**：扫描触发源与短路键迁移 §12 完整定义；health 四态 §11。

**需补足**：

| 补足项 | 组件 |
|---|---|
| 升级操作与扫描状态联动（未通过不可升级 / 可配置放行） | web |
| 被下发技能的来源约束：建议要求来自受保护分支或官方 org，避免"无审核直推 main 即刻进入团队"（§4.8.1 的开放性对下发场景收紧） | web / gitea |

**判定**：🔧 —— 与 D2 的 pin 结合后，"未经确认的内容进入团队"这条路径被结构性关闭。

### D4.5 我在组织树上只看到我管得着的范围，并自由选子树或个人

> 作为部门主管，我希望打开下发面板时只看到我管辖的组织子树，并能选整棵子树、某个子部门、或树里的具体某个人，以便按实际管理边界精准投放。

**现状机制**（这是一套已经跑通、且设计上很轻的能力，Git 方案不应破坏它）：

1. **入口闸门** —— `GET /distributions/my/authority` 返回 `DistributionAuthority{Unlimited, Departments[]}`：平台管理员 `Unlimited=true`（全树）；主管返回其管辖的子树列表；空列表则前端不显示下发入口（`distribution_service.go:166-193`）。
2. **管辖范围如何推导** —— 纯拓扑规则，**不依赖 leader_id / 职位 / 工号**：用户所属部门若是**非叶子节点**（有子部门），即视为该部门整棵子树的管理者；叶子部门成员（一线员工）不管辖任何范围（`ledDepartmentsFor`，`:194-229`）。
3. **树的浏览** —— dept-sync 提供 depth-1 懒加载（`GetChildren`，`deptsync/client.go:214`，PR #173），大组织树可逐层展开而不必一次拉全量。
4. **选择粒度** —— 请求体是 `targets[]`，每项 `{scopeType: user|department, targetID}`：选子树 → `department`（服务端用 `include_children=true` 展开整棵子树，`client.go:290`）；选个人 → `user`。**同一次下发可混合多个目标**。
5. **人员检索** —— `GET /distributions/eligible-users?keyword=` 按管辖范围过滤后返回候选人（`ListEligibleUsers`，`:230-283`）。
6. **越权兜底** —— 提交时 `AuthorizeTargets` 逐个校验目标是否落在管辖 `dept_path` 前缀内（`:302-333`），前端可见性与后端授权是两道独立防线。
7. **失败姿态** —— dept-sync 不可达时 fail-closed：非管理员得到空管辖范围，而非过宽范围（`:127-129`）。

**Git 方案下的流程**：以上七步**全部落在 costrict-web 的 DB 与 dept-sync 之间，不经过 Gitea**。V4 迁移后：

1. **server** authority 解析、树浏览、目标选择、越权校验逻辑原样保留。
2. **server** 唯一变化在下发提交之后——按 D1 锚定 `pinned_sha`、按 D9 传递内容授权。
3. **portal** 树选择器交互不变；可增强为在选择时预估覆盖人数（见下）。

**V4 已支持**：V4 未涉及部门模型，因此不构成冲突；`§C.2.1` 的"保留下发语义"覆盖这条链路。

**需补足**：

| 补足项 | 组件 |
|---|---|
| 📌 部门真相源确认：V4 §8「业务线层级」与 identity-tenant 的 team/org 统一之后，dept-sync 是否仍是部门与管辖关系的真相源。若换源，`ledDepartmentsFor` 的拓扑推导规则需在新模型里等价重建 | 架构决策 |
| 若走 D9 的 collaborator 授权路线：选中一棵万人子树时是 N 次 Gitea 授权调用，树选择器需在提交前给出人数预估与批量确认（与 L1-14 规模问题同源） | web / portal |
| 覆盖人数预估接口（选中节点即时返回可达人数、以及其中未登录/不可达的数量），与 D8 的未覆盖名单形成闭环 | web / portal |
| 管辖范围随组织调整的时效：现状依赖 dept-sync 短 TTL 缓存，reorg 后下一次刷新生效（已是有意的权衡）；建议在 D5 的对账 JOB 中一并复核既有下发的管辖合法性 | web |

**判定**：✅ 天然满足（机制与 Git 方案正交，迁移不破坏）+ 🔧 可增强（人数预估、规模化授权）

### D5 部门有人来了、有人走了，下发自动跟上

> 作为下发者，我希望部门下发对新成员自动生效、对调离成员自动收回，以便不用手工维护名单。

**Git 方案下的流程**：成员对账 JOB 定期比对 dept-sync 成员与 receipt 集合，补发新增、回收调离（server，纯 DB 层）。

**V4 已支持**：不涉及（部门解析不在 V4 范围，Git 方案不妨碍）。

**需补足**：

| 补足项 | 组件 |
|---|---|
| 成员对账 JOB（补发 / 回收 / 未登录用户首登补发） | web |
| 同一 JOB 顺带处理 `expires_at` 到期（现状该字段只写不读） | web |

**判定**：🔧 —— 与 Git 无关的独立补足项，但值得和 D3 的落后检测做进同一个调度框架。

### D6 我收回下发，团队环境干净退场

> 作为下发者，我希望收回后接收方本地不再有这个技能，以便控制生命周期闭环。

**Git 方案下的流程**：

1. 面板点收回 → DB 状态 `revoked`、删接收方 favorite（server，现状逻辑保留）
2. 接收方客户端 orphan 检测 → 卸载：注销命令 + 删运行副本（csc，现状已有）
3. 若下发时授过 Gitea collaborator（私有技能），收回时同步撤销（server → gitea）

**V4 已支持**：收回状态机不变。

**需补足**：

| 补足项 | 组件 |
|---|---|
| 卸载时同步清理缓存副本（现状 `removeItemFromConfig` 的 `_localPath` 参数未使用，`~/.costrict/favorites/` 下残留） | csc |
| 收回联动 Gitea 授权撤销（若走 collaborator 路线） | web / gitea |
| 对"已 clone / 已另存"的副本：明确产品口径——公开内容不承诺物理回收（与现状一致）；敏感内容用 private + pinned + 授权回收组合 | 产品口径 |

**判定**：🔧 —— 运行副本的回收现状已可用；补缓存清理与授权联动后闭环完整。

### D7 技能出了安全问题，我能快速止血

> 作为平台管理员，当某技能被扫出风险，我希望已下发/已订阅的用户尽快停用它，以便控制爆炸半径。

**Git 方案下的流程**：

1. `[V4 §11.2]` 扫描 / check hook 判定 `polluted`，记录引入 commit（server）
2. `[V4 §11.3]` health 状态透传到多个触点：发现层 API 默认不返回 `polluted`（需显式 `?include=polluted`）、`unknown` 永不返回；marketplace 卡片灰显；详情页 banner + issues + 引入 commit 链接；下发 manifest 内嵌 `health` 字段（server / portal）
3. `[V4 §11.5]` 客户端按消费端策略处理：runtime 对 `polluted` 接受+显著告警、对 `unknown` 拒绝（csc）
4. `[V4 §11.8]` 状态跃迁触发通知：`clean → polluted` 通知 owner + 业务线 editors + watchers（站内 + email）（server）

> **V4 的治理哲学是"软治理 + 状态透传 + 消费端决策"**（§11 标题即"不阻断"）。§11.8 明确把「polluted 持续 30 天未处理的自动降级」列为 out of scope。因此本节不提出平台侧的阻断式处置。

**V4 已支持**：health 四态状态机、触发规则矩阵（§11.2）、多端透传（§11.3）、消费端策略（§11.5）、告警通知（§11.8）——这套治理资产正好补上现状"扫出问题后无任何动作"的空白（现状 `SecurityStatus` 仅用于列表筛选，`capability_item.go:984`）。

**需补足**：

| 补足项 | 来源 | 组件 |
|---|---|---|
| health 透传落点：§11.3 提到"下发 manifest"，但现状下发链路无 manifest 概念——需确定挂载点（建议挂现有列表/详情响应，客户端改动最小） | `[推导]` | web / csc |
| 暂停恢复对客户端生效的判据修正（现状 resume 不变更 `createdAt`，客户端 watermark 不感知；补 `redeliver_at`） | `[现状缺陷]` | db / web / csc |
| 下发者纳入通知范围：§11.8 的通知对象是 owner/editors/watchers，未含"已下发该能力的主管"。让下发者知情是必要的 | `[推导]` | web |

**判定**：🔧 —— V4 的 health 体系落地后，下发者从"完全不知情"变为"状态可见 + 主动通知"。

> ⚠️ 本节先前版本提出的「管理面板一键暂停所有关联下发」已移除——V4 §11.8 明确将自动降级列为 out of scope，阻断式处置与其治理哲学冲突。若确有需求，见文末「可选增强」E-1。

### D8 我想知道下发到底覆盖了谁

> 作为下发者，我希望知道这次下发实际覆盖了多少人、谁没覆盖到，以便判断是否需要补救。

**现状**：

- `[现状]` 下发返回 `RecipientCount`（`distribution_service.go:512`）——**已提交后**的实际收件人数
- `[现状]` 管理端可查全平台下发与逐条 receipt（`/admin/distributions/:id/receipts`）
- `[现状缺陷]` 部门下发时，dept-sync 成员中未登录过平台的人被静默跳过（`distribution_service.go:556`，注释原文 "silently skipped — not an error"），差额不可见
- `[现状]` receipt 状态枚举含 `accepted`（`models.go:823`），但下发侧从未写入该值（全代码仅 invitation 模块使用该字面量）——设计时预留过"已接受"语义，未落地

**Git 方案下的变化**：

`[推导]` 内容按 sha 锚定后，"接收方拿到的是哪一版"第一次可被精确表达——这是现状（版本靠 frontmatter 字符串）结构上做不到的。是否要利用这一点做端到端对账，是独立的产品决策，见「可选增强」E-2。

**需补足**：

| 补足项 | 来源 | 组件 |
|---|---|---|
| 下发结果返回未覆盖名单与原因（未登录 / 不在部门 / 解析失败），补上被静默丢弃的差额 | `[现状缺陷]` | web |

**判定**：🔧 —— 仅需修复现状的静默丢弃；更强的对账能力属可选增强。

> ⚠️ 本节先前版本提出的「客户端上报 `installed_sha` 生效回执」已移出主线——V4 全文无回执/生效状态概念（grep 零命中），该功能与 Git 迁移无依赖关系。见「可选增强」E-2。

### D9 我下发私有技能，接收方拿得到内容

> 作为下发者，我希望私有仓库里的技能下发后接收方能正常使用，以便敏感能力也走统一通道。

**Git 方案下的流程**（两条候选，📌 需决策）：

- **方案一（授权下沉）**：下发时 server 用 admin PAT 给接收方授 Gitea collaborator（read），收回/过期时撤销。Gitea 侧权限自洽，`git clone` 也可用。
- **方案二（受理旁路）**：内容读取的权限判定增加一条旁路——存在 active 且未过期的 distribution receipt 即放行，server 用 service PAT 代取内容。Gitea 不感知下发，状态机完全留在 costrict-web。

**V4 已支持**：§4.7 permission 反查、§7.2 admin PAT 场景清单（方案一需把"下发授权"加为第 3 个场景）。

**需补足**：

| 补足项 | 组件 |
|---|---|
| 二选一决策：方案一表达不了 paused/expired 的细粒度（需靠撤销时机弥补）；方案二需在 §4.7「纯 Gitea 透传」上开一个显式例外 | 📌 架构决策 |
| 万人级下发时方案一是 N 次 Gitea API 调用（§10.7 限流 per-repo ≤ 20），需异步批处理 | web |

**判定**：📌 —— 两条路都能跑通，需要与 V4 作者定一条。倾向方案二：下发状态机（暂停/过期/部门）只有 costrict-web 能表达。

### D10 下发的粒度：整包还是单个能力

> 作为下发者，下发一个 plugin 时，我希望明确团队拿到的是什么；必要时我想只推包里的某一个 skill。

**现状**：plugin 的子 skill 会被提升为独立 item 行（`parent_plugin_id` 关联），理论上可单独下发。
**V4 立场**：§2.2「不下钻 plugin 内部」——pack 整体是一个能力项，server 不解析、不索引子文件。

**需补足**：

| 补足项 | 组件 |
|---|---|
| 粒度决策：跟随 V4（下发只到 plugin 整包，客户端负责包内启停）或保留子项模型（V4 的同步粒度需为此开例外） | 📌 架构决策 |
| 存量子 skill 行（已被收藏/下发的）的迁移归属 | web / db |

**判定**：📌 —— 两个方向都成立；若跟随 V4，需要给"包内启停"补客户端交互。

## 可选增强（`[新增建议]`，非 V4 范围）

以下条目**既非现状能力、也非 V4 提案内容**，是本文基于审计发现的问题提出的产品增强。它们与 Git 迁移**没有依赖关系**，可独立立项或直接否掉。评审 Git 方案时可跳过本节。

| # | 增强 | 动机 | 与 V4 的关系 | 组件 |
|---|---|---|---|---|
| **E-1** | health 劣化时平台侧主动暂停关联下发 | 现状扫出风险后无任何处置手段 | ⚠️ **与 V4 §11 治理哲学冲突**——V4 主张"不阻断 + 状态透传 + 消费端决策"，§11.8 明确把自动降级列为 out of scope。若要做需先与 V4 作者对齐 | web |
| **E-2** | 端到端生效对账：客户端上报 `installed_sha` + 面板显示每个接收方的实际版本 | 现状"管理端显示下发成功"与"用户实际能用"之间无反馈闭环 | V4 无此概念；但 sha 锚定让它第一次可精确实现 | db / web / csc |
| **E-3** | 下发落后检测 JOB + 批量升级操作 | 作者发新版后下发者不知情 | V4 的 compare API（§10.2）仅用于 sync worker 拉变更清单，无面向下发者的用途；diff 预览属能力复用，落后检测与批量升级是新功能 | web |
| **E-4** | 选中组织节点时预估覆盖人数 | 现状 `RecipientCount` 是下发后才返回 | V4 无关 | web / portal |
| **E-5** | 下发版本策略中的"跟随最新"模式 | 部分场景希望自动跟随 | V4 无关；注意它与 E-1 缺失时的风险叠加（无审核 + 自动跟随） | db / web |

> 建议取舍顺序：E-2 解决的是真实痛点且不与 V4 冲突，优先级最高；E-1 需先解决与 V4 治理哲学的分歧；E-3/E-4/E-5 属锦上添花。
